## 1. 启动时间线（生产构建，单次采样）

测量方式：`npm run build` 后 `npm run start`（`electron-vite preview`），`ELECTRON_ENABLE_LOGGING=1`，探针用 `performance.now()`（相对导航开始）打点。

| 里程碑 | 距导航开始 |
| --- | --- |
| 渲染包解析并执行完成 | **299 ms** |
| Vue 挂载完成 | 328 ms |
| 阶段行「正在准备地形数据…」/ Viewer 创建 / 影像层挂载 | 533 ms |
| 瓦片请求开始 | 1290 ms |
| 阶段行「正在加载地图瓦片…」/ **地球可见** | **1294 ms** |
| **加载卡片消失** | **20549 ms** |

**读法：应用代码与地球在 1.29 秒就绪，但用户要盯着加载卡片等 20.5 秒。**

这 20.5 秒不是代码慢，而是**瓦片始终没有 settle，一直等到 20 秒超时兜底**。根因已实测：本机网络下配置的默认底图 `esri-imagery` 与 `tile.openstreetmap.org` **连接超时（10 s connect timeout）**，而 `elevation3d.arcgis.com`（地形）可达（250–670 ms）。即**就绪判定依赖瓦片 settle，底图不可达时必然等满超时**。

> 这既是性能问题也是可用性问题：在默认底图被墙的网络环境下，这条路径就是"启动慢 20 秒"的全部来源。

参考：dev 模式下同样的里程碑分别为 8474.9 / 8553.2 / 9096.8 / 10252.2 / 30048.4 ms。dev 模式按模块逐个请求，**不能作为启动基线**。

## 2. 空闲开销（正文 §二.2 的量化）

| 指标 | 实测 |
| --- | --- |
| **完全静止时的帧率（t15）** | **54.6 fps** |
| 渲染像素吞吐 | 2520 × 1680 × 54.6 ≈ **233 MP/s**（集成显卡） |
| 渲染进程 JS 堆 | 77.6 MB used / 141.1 MB total |
| 启动即加载的实体 | **442 个**（＝标注存档里的 442 条标注：441 点 + 1 折线） |
| 专题数据源 | 0（未开启任何专题图层） |

**应用空闲时仍在满速渲染。** 叠加 `useBrowserRecommendedResolution: false`（强制按物理分辨率渲染）与 `preserveDrawingBuffer: true`，这是待机发热／耗电最直接的解释。

> t60 采样得到 0.0 fps，疑似窗口被遮挡触发节流，**待可见窗口复测**，暂不作为结论。

## 3. 包体与编译成本（正文 §二.1 的量化）

| 项 | 实测 |
| --- | --- |
| 渲染主 chunk | **15,157.71 kB（15.16 MB）**，8,236 模块 |
| `SearchSources` 分包 | 1,202.09 kB（React + antd） |
| 渲染 CSS | 114.92 kB |
| 主 chunk V8 解析+编译 | **429 ms** |
| `SearchSources` 分包解析+编译 | 37 ms |

Cesium 1.145.0 的包结构已核对：`exports["."].import = ./Source/Cesium.js`，而该入口是 **0.07 MB 的逐模块桶文件**（`Build/Cesium/Cesium.js` 为 5.74 MB、`Build/Cesium/index.js` 为 4.53 MB）——**结构上可 tree-shake**。当前 15 处使用 `import * as Cesium`（命名空间导入），是把整库打进主 chunk 的直接原因。

**待确认**：生产构建日志中大量出现 `antd`（React）模块的 module-directive 告警，需要确认 antd 是否也混入了主 chunk（未测）。

## 4. 瓦片缓存与主进程 I/O（正文 §二.5 的量化，用户真实数据）

| 项 | 实测 |
| --- | --- |
| 缓存瓦片数 | **28,024 张** |
| 缓存体积 | **376.01 MB**（平均 13.74 KB/张） |
| userData 总计 | **800.60 MB / 59,086 文件**（另含 Chromium HTTP 缓存 338 MB、Code Cache 71 MB） |
| `readTile` 同步读（命中路径） | **0.97 ms/张**（2×`existsSync` + `readFileSync` + `JSON.parse` + `readFileSync`） |
| `writeTile` 同步写 | **1.29 ms/张**（递归 `mkdir` + 2×`writeFileSync`） |
| **`cacheStats()` 遍历真实缓存** | **4,053.57 ms（4.05 秒）** |

**一次缓存统计就要阻塞主进程 4 秒**；每张瓦片的读写都在主进程同步执行，100 张瓦片的视野切换约 100 ms 主线程停顿。缓存自身也没有上限，已累积到 376 MB / 2.8 万文件。

## 5. 修正正文中的两处判断

| 正文判断 | 实测结果 |
| --- | --- |
| §二.7「启动链路含一次远程地形元数据解析……具体秒数需重测」（暗示可能耗时数秒） | **不是瓶颈**：地形元数据实测 **250–670 ms** |
| §二.5 把 JSON 存储（会话历史美化重写、标注/场景整文件读写）列为同步 I/O 热点 | **当前规模下可忽略**：`ai-chat-history.json` 0.31 MB（2 会话 / 14 消息）→ `JSON.stringify(pretty)` **2.61 ms**；`annotations.json` 0.24 MB（442 条）→ **1.92 ms**；`earthquakes.json` 0.09 MB（522 事件）→ **0.44 ms**。仅作为数据增长后的预防项 |

另有两处细节需按代码修正：

- §二.5 写「写入时 `mkdirSync` + 两次 `writeFileSync` + `renameSync`」——**瓦片写入路径不含 `renameSync`**（`renameSync` 用于标注／场景文档）。
- §八表格中的 14,432.93 kB / 7,822 模块 / CSS 67.49 kB 已被当前分支取代（见本评论第 3 节：15,157.71 kB / 8,236 模块 / 114.92 kB）。
